Status: **approved after plan reviews, 2026-10-11** (CEO review in SCOPE REDUCTION mode and engineering review, each with a Codex outside pass; decisions D1 to D28 and corrections F1 to F25 are one commit per batch in this file's history; the review records live in gstack's project folder). Earlier: v0, approved as the spec on 2026-10-10 in the spec session. When this file and an ADR disagree, this file wins and the ADR is updated. ADRs (why): `docs/adr/0001-read-only-by-construction.md`, `0002-checks-run-as-the-tenant.md`, `0003-cite-kubectl-mtb-do-not-fork.md`, `0004-four-verdicts-and-exit-codes.md`, `0005-probes-carry-sizes-and-a-control-probe.md`, `0006-rollout-headroom-counting-rules.md`, `0007-at-09-requires-the-psa-label.md`, `0008-policyreport-v1alpha2.md`, `0009-identity-is-what-the-api-server-says.md`. Terms: `GLOSSARY.md`.

Terms used below. AT: the prefix of every check ID (`AT-01` to `AT-10`); it stands for audit-tenant. SSAR: SelfSubjectAccessReview, an API call that asks the cluster "may this identity do X?" and does nothing. Dry-run: a create request with `dryRun=All`; the server runs every gate and stores nothing. Admission: the gate that inspects a new object before it is saved. PSA: Pod Security Admission, the built-in pod gate switched on by a namespace label. MTB: the archived Kubernetes Multi-Tenancy Benchmarks. PolicyReport: the `wgpolicyk8s.io` report object that policy dashboards read.

## 1. Problem

A platform team runs one Kubernetes cluster for many teams ("tenants"). Security and auditors ask: "prove that team A cannot touch team B". Tenants ask: "is my namespace set up right, and why was my pod rejected?". Today nobody can answer from the tenant's side. Admin-side scanners (Kyverno audit mode, Kubescape, Polaris, Popeye) infer what a tenant could do from rules; they never ask the cluster as the tenant. Permission viewers (rbac-tool, who-can, rakkess) show RBAC only. NamespaceHound (Wiz, 2024) enumerates cross-namespace escape paths, again from the admin side. The community tool that did ask as the tenant, `kubectl-mtb`, is archived (last release December 2021) and predates PSA. `kuota-calc` computes a quota from manifests but never compares it with the live namespace. Checked 2026-10-10: krew lists 411 plugins; none runs as the tenant.

`kubectl audit-tenant` runs ten checks as the tenant identity against one namespace and prints one verdict per check, with the layer that decided it, the matching MTB ID, a reason, and a hint. It never changes the cluster.

## 2. Users and first adopters

**Primary user: the platform team.** Mature platforms hide Kubernetes from application teams; many tenants never hold a kubeconfig, and a rejected pod becomes a message in the platform team's chat channel, not a kubectl error. For those platforms this tool is a test of the platform's own fences. The provisioning pipeline runs it right after it creates a namespace, impersonating the new tenant's identity, and fails the pipeline on a FAIL. Security or an auditor runs it on demand against any namespace and gets one page with a public benchmark ID per line. The team that wrote the guardrails should not be the only proof that they work; this checks their automation from the outside, the way an integration test checks code.

**Secondary users: tenants who do hold a kubeconfig.** Most namespace-per-team clusters on EKS, GKE and AKS, Capsule tenants and Rancher projects still hand out kubectl. Those teams run it against their own namespace with no special permission and read why a pod was rejected instead of asking in a channel.

**Why not build these checks into the platform's deploy code?** Good platforms do. This tool is the independent check on those checks: a standard list that names each fence with a public benchmark ID, runs in ten seconds against any cluster, and does not depend on the platform's own code being right. Teams that have the guardrails use it as the test. Teams that do not have them yet use it as the list.

| User | Runs it how | Wants |
|---|---|---|
| Platform engineer, at tenant onboarding | pipeline step: `kubectl audit-tenant -n team-a --as team-a-admin -o json --fail-on-skip`, exit code gates the step | Proof that the new namespace is fenced before the tenant gets it |
| Security or auditor | `kubectl audit-tenant -n team-a --as team-a-admin` | One page of PASS/FAIL with benchmark IDs, repeatable next quarter |
| Tenant team with kubectl | `kubectl audit-tenant -n team-a` with its own kubeconfig | "Is my namespace governed?" and "why was my pod rejected?" |
| Policy dashboard owner | `-o policyreport \| kubectl apply -f -` | The verdicts next to Kyverno results in Policy Reporter |

First adopters: three platform engineers at other companies (interviewed before the build goes far, see section 10), community meetup members with shared clusters, and Capsule users. The quick start must work on a kind cluster in five minutes.

## 3. Scope (v0.1)

**In.** Ten checks (section 5). Two identity modes: self (current kubeconfig identity) and impersonation (`--as`, `--as-group`). Four verdicts: PASS, FAIL, SKIP, ERROR (ADR 0004). Outputs: checklist (default), `-o wide`, `--plain`, `-o json`, `-o policyreport`. Exit codes for CI. Subcommands `list-checks` and `version`. Binaries for darwin and linux (amd64, arm64) and windows/amd64. krew manifest. Unit, envtest and kind end-to-end tests.

**Out (goes to `TODOS.md` as "later").** Network behavior tests (need running pods). Writing the PolicyReport into the cluster. Capsule `Tenant` discovery. SARIF. Gatekeeper constraint mapping. Helm chart or operator. Many namespaces or clusters in one run. `--baseline` file (v0.2). Argo Rollouts in the headroom math (v0.2; deferred in the CEO review of 2026-10-10, ADR 0006). DaemonSets, Jobs, CronJobs and bare Pods in the headroom math (ADR 0006). Cloud lookups for service principals (ADR 0009). Checking whether the network plugin enforces NetworkPolicy.

**Fallback.** If v0.1.0 is not tagged by 2026-10-31, tag with whatever passes, minimum AT-01, 02, 03, 04, 05, 06, 09: every behavioral isolation check plus quota and PSA presence. AT-10 is the heaviest and least security-critical check, so it is the first to wait for the next tag (swapped in the eng review, 2026-10-11, D28). The README's check table and `list-checks` show only shipped checks, and the acceptance criteria in section 12 apply to the shipped set. Checks never ship half-done: a check is in or out.

Rules that shape the code:

- **Read-only by construction (ADR 0001).** `internal/safety.Transport` wraps the REST transport with an exact allowlist, not a verb rule, because GET is not read-only in Kubernetes (`pods/exec`, `attach`, `portforward` and `proxy` are GET upgrades). Allowed: GET `/version`; GET `/api/v1/namespaces/<target>`; GET (list) of `resourcequotas`, `limitranges`, `networkpolicies`, `deployments`, `statefulsets` and `horizontalpodautoscalers` in the target namespace; POST to `selfsubjectaccessreviews` and `selfsubjectreviews`; POST to `pods` or `services` in the target namespace only when the query has `dryRun=All` (the transport guarantees the flag leaves the client, not that every hop honors it, D79). So the transport also checks every pods and services answer (D101, D103). A rejection (a 4xx other than 429) stores nothing. A 2xx is a verified dry run only when its `metadata` has a generated `audit-tenant-probe-` name and no `resourceVersion`. After the first create answer that is neither (a 2xx that fails that test, an unreadable or oversized answer, a failed send, a 429, a 5xx or any other code), the transport refuses every later create in the run with "no further create", so a hop that drops the flag can store at most one object. It also removes `Retry-After` from create answers, because client-go resends a POST answered 429 or 5xx with `Retry-After` up to 10 times. A new check that creates needs no code of its own for this: the transport enforces it, and the check reports it. Everything else is refused before it leaves the process: every subresource, any `secrets` path, any other namespace, and any PUT, PATCH or DELETE; a refusal is a bug in the tool. The test (section 8) drives a real clientset through the transport against an `httptest` server, replays every check, asserts that only allowlisted requests passed, and asserts that a deny-list of crafted requests (a pod `exec` GET, secrets GET and LIST, PATCH, DELETE, POST without `dryRun`, a request to another namespace) is refused.
- **Run as the tenant (ADR 0002).** Behavioral checks ask the cluster. The tool never reads Roles or policies to guess.
- **Fixed order, sequential.** Checks run one after another in ID order. About 35 requests per run. No concurrency in v0.1; a full run on kind must finish in under 10 seconds (section 7). The client uses QPS 50 and burst 300 (kubectl's values); client-go's defaults (5 and 10) would throttle the run.
- **One LIST per kind per run.** `resourcequotas` and `limitranges` are listed once and cached for the run; AT-06, AT-07, AT-10 and the probe sizing read the cache. The namespace object is read once at startup (section 6) and AT-09 reads the cached result.
- **One `--timeout` (default 30s)** bounds the whole run through a context deadline. `--request-timeout` (cli-runtime) bounds each single request; when both are set, the shorter one wins for that request.
- **No Argo Rollouts in v0.1.** AT-10 counts only built-in workload kinds, so the tool needs no dynamic client and no discovery call. Rollouts return in v0.2 (`TODOS.md`), read as unstructured objects without an Argo Go module.
- **Go style.** Code follows the JetBrains modern Go guidelines (agent skill `/modern-go-guidelines:use-modern-go`, loaded before any Go is written) and `golangci-lint` enforces what it can.
- **Stdlib first.** `text/tabwriter` for columns, `golang.org/x/term` (already a client-go dependency) to detect a terminal, hand-written ANSI for the four colors. No table or color library.

Go module: `github.com/BodhiSatvik/kubectl-audit-tenant`. Go 1.26. `k8s.io/client-go`, `k8s.io/api`, `k8s.io/apimachinery`, `k8s.io/cli-runtime` v0.37.x. `github.com/spf13/cobra`. Supported servers: Kubernetes 1.28 and newer (SelfSubjectReview is GA from 1.28). Import `_ "k8s.io/client-go/plugin/pkg/client/auth"` so cloud logins work (krew best practice).

## 5. The checks

Severity is static per check and appears in `-o json`, `-o policyreport`, and `list-checks`. Every non-PASS result carries a reason (the cluster's own text where possible) and a hint.

| ID | Name | Kind | MTB | Severity | Method | PASS when |
|---|---|---|---|---|---|---|
| AT-01 | No cluster-scoped access | behavioral | MTB-PL1-CC-CPI-1 | high | SSAR with no namespace (these resources are cluster-scoped; a namespaced SSAR draws an API warning): `list nodes`, `create namespaces`, `create clusterrolebindings`, `create persistentvolumes`; before a PASS, a positive control, `create selfsubjectaccessreviews`, which any API server allows (a bare no is ERROR: something other than the API server answered, D55; a no with `denied: true` came from an authorizer such as an access proxy with its own roles, so the PASS stands and its reason names the denied control, D57). A proven grant is FAIL without the control | all four denied |
| AT-02 | No cross-namespace secret access | behavioral | MTB-PL1-CC-TI-2 | high | SSAR: `get secrets`, `list secrets` and `watch secrets` in `--other-namespace` (default `kube-system`; a watch also streams every secret body, D66) | all denied. SSARs carry no resource name, so a grant limited by `resourceNames` to specific secrets is not detected; the PASS reason says "no general get, list or watch on secrets in kube-system" and its note "not tested: grants limited to named secrets (resourceNames)" (D86, D92) |

### Probes (AT-04, AT-05), ADR 0005

- Image `registry.k8s.io/pause:3.10` (never pulled: dry-run stores nothing). Container `probe`. Sizes follow the namespace's LimitRange (ADR 0005): requests and limits are always stated, `1m` CPU and `1Mi` memory raised to the highest LimitRange `min`; if limitranges cannot be listed (403), `1m`/`1Mi`; any other list error is ERROR. Probes never rely on LimitRange defaults, because the API server copies `max` into `default` and `defaultRequest`, so an unsized probe would ask for the max (D85). The control pod uses the same rule. `generateName: audit-tenant-probe-`, label `app.kubernetes.io/managed-by: audit-tenant`, annotation `audit-tenant.dev/probe: "true"`.
- The **control pod** is PSA-restricted compliant: `runAsNonRoot: true`, `runAsUser: 65532`, `allowPrivilegeEscalation: false`, `capabilities.drop: ["ALL"]`, `seccompProfile: RuntimeDefault`. Each dangerous probe is the control pod plus exactly one dangerous capability. The API server rejects `privileged: true` with an explicit `allowPrivilegeEscalation: false` at validation, so every privileged probe differs from the control in that field too; AT-04.1 therefore sends two forms, `privileged: true` with `allowPrivilegeEscalation` unset (D70) and with it `true`, and passes only when both are rejected (D78). AT-04.5 sets only `allowPrivilegeEscalation: true` (D78). A PASS carries a note naming what the probe did not test: AT-04.1 and AT-04.5 test a regular container only (not initContainers or ephemeral containers, D97), AT-04.2 a hostPath of `/` only (not allowed path prefixes), AT-04.4 not `hostPort`. Notes are their own field, printed on a `note` line under the result and never cut with the reason (D86); every "not tested" text in this section is such a note. A result whose forms are probed stops at its first FAIL (D84). Every accepted dry-run answer, not only the control's, must carry an empty `resourceVersion` and a generated name; otherwise the check stops with ERROR naming the stored object, and the run sends no further create (D79, D84, D101, D103).
- Order, AT-04: (1) SSAR `create pods` in the target namespace. Denied → SSAR `create`, `update` and `patch` on `deployments`, `replicasets`, `statefulsets`, `daemonsets` (group `apps`), `jobs`, `cronjobs` (group `batch`) and `replicationcontrollers` (core), then `update` and `patch` on `pods/ephemeralcontainers`, then `update` and `patch` on the `scale` subresource of `deployments`, `replicasets`, `statefulsets` and `replicationcontrollers` (D77), in the target namespace (31 SSARs, only on this branch, stopping at the first allowed one; scaling a controller up creates pods from its template; changing an existing controller's pod template also yields new pods, and an ephemeral container adds one to a running pod, D66). All denied → the no-rights anchor, `list pods` in the namespace, asked once per run and required before every RBAC-only PASS of AT-01 to AT-05 (D80): denied → AT-04.1 to AT-04.5 SKIP "this identity may not even list pods in <ns>, so an RBAC-only PASS would prove nothing", hint "check -n, --as and --as-group: the identity may be misspelled, miss its identity-provider prefix, or have no role in this namespace" (a misspelled `--as` user is denied everything, D69); allowed → PASS, layer RBAC, reason "RBAC denies create pods; create, update, patch and scale of the built-in pod controllers; and adding ephemeral containers; admission not exercised", note "not tested: ways to gain pod creation inside the namespace (creating Secrets, RoleBindings or service account tokens, impersonating its service accounts), grants limited to named objects (resourceNames), and controllers from CRDs (such as Argo Workflows or Tekton)" (D67, D77, D86). Any allowed → AT-04.1 to AT-04.5 SKIP, reason "RBAC denies create pods but allows <verb> <kind> in <ns>; pods a controller creates (or scales up), and containers added to running pods, bypass the tenant's create-pods RBAC, so admission must be the fence and it was not exercised", hint "run with --as <an identity that may create pods>, or confirm AT-09 and your policy engine cover controller-created pods". No probe is sent on either branch. (2) Allowed → dry-run the control pod. Rejected by admission, a quota or a LimitRange → AT-04.1 to AT-04.5 SKIP with the control's rejection text and the classifier's hint, else "the namespace rejects even a compliant pod; fix that first"; an answer the classifier calls ERROR (a 429 or 5xx, 401, a policy that could not evaluate, a malformed control, an unknown rejection, no answer; D95, D99) → ERROR, as any other API error (D65). (3) Control accepted, and its answer is a dry run (empty `resourceVersion` and a generated `audit-tenant-probe-` name; otherwise ERROR before any dangerous probe, naming a stored object to delete, D79; after any create answer that is not a verified dry run (section 4), no later check sends a create, and its results are ERROR "not run: an earlier create answer could not be verified as a dry run, so no further create was sent" with the hint "see the earlier ERROR that sent a create: delete any object it names, fix what it reports, then re-run", D101, D103) → dry-run the probes, one result each; a probe answered with 429, a 5xx or no answer ends the probes, and that result and every later one is ERROR, because the answer would repeat for each probe with client-go's retries (D91). The control pod gates only AT-04; it is sent only when at least one AT-04 sub-check is selected.
- Order, AT-05: (1) SSAR `create services`. Denied → SSAR `update` and `patch` on `services`; both denied → the `list pods` anchor of AT-04 (D69), then PASS, layer RBAC, reason "RBAC denies create, update and patch of services; admission not exercised", note "not tested: ways to gain service creation inside the namespace (RoleBindings, service account tokens), grants limited to named Services (resourceNames), and operators that create Services for the tenant" (D67, D77, D86); either allowed → SKIP, reason "RBAC denies create services but allows <verb> services; an existing Service can be changed to type NodePort, so admission must be the fence and it was not exercised", hint "run with --as <an identity that may create services>, or confirm your policy engine rejects type: NodePort on update". (2) `create services` allowed and no earlier unverified create answer in the run (D101, D103) → dry-run a compliant ClusterIP control Service (same generateName and labels, one port 80/TCP, no selector). Rejected → AT-05 SKIP with the control's rejection text and the classifier's hint, else "the namespace rejects even a plain ClusterIP Service; fix that first"; an ERROR answer → ERROR (D65). (3) Control accepted and verified as a dry run as in AT-04 (D79) → dry-run the NodePort service. Rejected by admission → PASS with the layer, and the note says "tested on create only: changing an existing Service to NodePort, and type LoadBalancer (which also opens node ports), were not tested" (D67, D74); accepted → FAIL.
- Because RBAC is settled by SSAR before any probe, a probe rejection is never attributed to RBAC.
- **Classifier** on a probe rejection, rules applied in this order, first match wins; every text rule, (1) to (4), applies only to an HTTP 4xx answer, because a 5xx is a failing backend, not a decision (D82, D84); before them, a 429 (Too Many Requests, which a webhook may also send to deny) or a 5xx is ERROR with the re-run hint "re-run; if it repeats, run with --debug and report the server message" (D95); then (2a) below, ahead of (1) and (1b), because a policy's evaluation error quotes the policy's own expression, which can contain any text (D102): (1) message contains `admission webhook` and `denied the request` (the API server's phrase; `denied` alone can be part of a webhook name) → PASS, layer admission (webhook), webhook name kept; it comes before (1b) because a webhook such as Kyverno's podSecurity rule quotes the PSA text; (1b) message contains `violates PodSecurity` → PASS, layer admission (PSA), the violated controls kept in the reason; (2a) message contains `ValidatingAdmissionPolicy` and one of the API server's evaluation-failure texts (`resulted in error`, `failed to configure`, `running out of cost budget`, `compilation error`, `runtime cost could not be calculated`, `internal error compiling expression`) → ERROR: the policy could not evaluate the probe (D84, D99); (2b) message contains `ValidatingAdmissionPolicy` and `denied request` → PASS, layer admission (policy), policy and binding names kept in the reason; (3) message contains `does not support dry run` or `sideEffects` → SKIP, hint names the webhook and the `sideEffects: NoneOnDryRun` fix; (3b) message contains `exceeded quota` and `services.nodeports` → PASS, layer admission (quota: name), when the `limited:` value is 0: the control Service uses no node port, so a zero quota is the NodePort fence itself (D68); a full quota above zero → SKIP, NodePort Services are allowed (D76); (4) message contains `exceeded quota` or `failed quota` (D82), or LimitRanger's ` usage per Container is ` or ` usage per Pod is ` (one violation or several in brackets) → SKIP (inconclusive; quota or LimitRange gate), hint says which; (5) HTTP 400 or 422 → ERROR (the probe itself is malformed; a bug to report); (6) any other rejection → ERROR with the full server text, never a guess; when the message is empty the reason is "HTTP <code> <reason>". A probe that is accepted (HTTP 200 or 201) → FAIL.
- AT-05 service: `type: NodePort`, one port 80/TCP, no selector, same generateName and labels.

### Headroom math (AT-10), ADR 0006

- Counted: Deployments, StatefulSets. Not counted in v0.1: Argo Rollouts (v0.2), DaemonSets, Jobs, CronJobs, bare Pods. The reason names each counted workload (`api 4->5 (HPA max)`) and shows each quota's `used` values so the reader sees what else consumes it; the note says the peak counts active pods during a rollout, that terminating pods can add to usage, and names the kinds not counted (D86, D106).
- Replicas: `spec.replicas` (default 1). If a `HorizontalPodAutoscaler` (autoscaling/v2) targets the workload (`scaleTargetRef` matched by API group, kind and name), use its `maxReplicas` instead. When several HPAs target one workload, the HPA controller scales none of them (`ScalingActive=False`, reason `AmbiguousSelector`, proven on kind): count `spec.replicas` raised to their largest `minReplicas`, and the note names the HPAs (D126).
- Peak pods: Deployment RollingUpdate = replicas + maxSurge (absolute, or percent of replicas rounded up; default 25%); Deployment Recreate = replicas; StatefulSet = replicas.
- Pod request and limit: if the pod template sets pod-level `spec.resources` (beta, on by default since Kubernetes 1.34), those requests and limits are the pod's values and the container sum is ignored; a pod-level limit with no pod-level request takes the containers' summed requests as the request, or the limit when no container requests that resource (the API server's `SetDefaults_Pod`, D110). Otherwise the Kubernetes rule: a container with a limit and no request counts its limit as the request (the API server defaults it so). Sidecars are init containers with `restartPolicy: Always`. Pod value = max(sum of app containers + sum of sidecars, max over ordered init containers of that container + the sidecars declared before it). Pod overhead from a RuntimeClass is not counted in v0.1 and the note says so when any workload names a RuntimeClass. A container with no request or limit takes the LimitRange `defaultRequest` or `default` for type Container if one exists, else 0, and the note says "N containers left a cpu or memory request or limit unset; counted as 0". Quota admission refuses a pod that leaves unset a value an unscoped quota tracks (`requests.cpu` or `cpu`, `requests.memory` or `memory`, `limits.cpu`, `limits.memory`: "must specify"), so such a workload is FAIL whatever the peak, reason "<quota> refuses the pods of deployment <name>: a container sets no <keys>" (D111). A webhook that sets sizes only on pods, not in the workload template, is not seen, so such a workload still FAILs and the hint says so; Kyverno mutate policies write the template through autogen and are seen (proven on kind, D120).
- Compare: for every unscoped ResourceQuota and each of the five keys it defines (`cpu`, `memory` and `count/pods` count as `requests.cpu`, `requests.memory` and `pods`), peak sum ≤ hard. FAIL reason: `tenant-a-quota requests.cpu: peak needs 6, hard is 4, short by 2 (deployments: api 3->4, worker 2->3)` (an ASCII arrow, so `--plain` stays ASCII). Assumes all workloads roll out at once; the FAIL hint says so.
- Edge cases, checked in this order: no unscoped ResourceQuota that sets any of the five keys → FAIL, reason "no ResourceQuota to compare against" (scoped quotas named if any), hint points at AT-06; then, no counted workloads → PASS, reason "no Deployments or StatefulSets; nothing to compare"; several LimitRanges → each missing value comes from the first LimitRange by name that sets it, as LimitRanger fills from every range, and the reason names only the ranges a container took a value from (D112, D121); a quota that defines only some of the five keys → only those keys are compared; cannot LIST deployments, statefulsets, resourcequotas or horizontalpodautoscalers → SKIP with the missing permission in the hint; cannot LIST limitranges while a counted container leaves unset a value an unscoped quota tracks → SKIP likewise (a value no quota tracks cannot change the verdict, D111); in both SKIP cases, if the partial sum already exceeds a hard value the verdict is FAIL, because the truth can only be worse; except while the HPAs are unreadable, since an HPA's `maxReplicas` can be below `spec.replicas`, so that case stays SKIP and its reason says the partial shortfall is not proven (D110). Every AT-10 PASS, FAIL and SKIP reason starts with "estimate: " (an ERROR reports a failed request, not an estimate), kept short so the checklist shows the numbers; the note carries the caveat "the peak counts active pods during a rollout; terminating pods can add to usage; not counted: DaemonSets, Jobs, CronJobs, bare Pods and Argo Rollouts" (D106).

## 6. Interfaces

### Command surface

```
kubectl audit-tenant -n NAMESPACE [--as USER] [--as-group GROUP ...]
                     [-o checklist|wide|json|policyreport] [--plain] [--no-color] [--debug]
                     [--fail-on-skip]
                     [--checks ID,...] [--skip ID,...]
                     [--other-namespace kube-system] [--timeout 30s]
kubectl audit-tenant list-checks [-o table|json]
kubectl audit-tenant version
```

Also honored: `--kubeconfig`, `--context`, `--cluster`, `--user`, `--request-timeout` (from cli-runtime), `KUBECONFIG`, `NO_COLOR`. `-h`/`--help` usage text starts with `kubectl audit-tenant`.

`--debug` writes to stderr one line per API request (method, path, HTTP status, duration), the identity resolution steps, and the full server body of every SSAR and probe response, plus the SelfSubjectReview answer without `status.userInfo.extra` (identity-provider claims; an answer that is not JSON is not shown; D51). It never prints request headers. stdout and the exit code are unchanged, so `-o json | jq` still works. The safety transport's request recorder (section 4) is its source.

Selection rules: `--checks` keeps only the listed IDs (families like `AT-04` or sub-checks like `AT-04.2`), then `--skip` removes IDs from that set; an unknown ID in either flag exits 2; an empty final set exits 2 with "no checks selected". `-n` omitted → the namespace of the current kubeconfig context; none set → exit 2 "namespace required". The run proceeds even when the namespace cannot be read by the identity (behavioral checks need no read); AT-09 then reports SKIP.

Startup: the tool first calls the version endpoint (unreachable → exit 2 "API server unreachable: <error>"; HTTP 401 → exit 2 "unauthorized: the cluster rejected your credentials (expired token?); log in again and retry"), then POSTs a SelfSubjectReview (HTTP 403 or 404 → identity falls back to the kubeconfig and `--as` values, marked `unverified`), then GETs the target namespace once (HTTP 404 → exit 2 "namespace <n> not found in context <ctx>; check -n or --context"; HTTP 403 → the run proceeds and AT-09 reports SKIP from this cached answer; any other error → exit 2 "could not read namespace <n>: <error>", because the namespace may not exist and every check would audit nothing), then sends one of AT-01's SSARs (`list nodes`, whose answer AT-01 reuses); if that SSAR itself is refused with 403, the identity cannot ask "may I?" at all and the run exits 2 with the hint "this identity lacks `create selfsubjectaccessreviews`, which every authenticated user normally has". Startup runs under the same deadline and signal handling as the checks: client construction and the first requests execute on a goroutine the run waits on with the context, so a hung exec credential plugin (a cloud login) or a server that never answers ends with exit 2 "timed out during startup: the credential plugin or the API server did not answer within <timeout>" instead of a hang. Before the SSAR hint applies, any startup 403 whose message contains `cannot impersonate` exits 2 with "<user> may not impersonate <--as value>: ask a cluster admin for `impersonate` on users, groups and serviceaccounts, or run without --as".

Failure rules: a read that the API server refuses with HTTP 403 is a fact about the identity, so the check reports SKIP with the missing permission in the hint (AT-06 to AT-10 for their own objects; AT-10 is SKIP when it cannot list HPAs, or LimitRanges while a counted container leaves a tracked value unset (D111), unless the partial sum already exceeds the quota, which is FAIL, except while the HPAs are unreadable, D110). Any other API error makes the check ERROR. The whole run has one deadline (`--timeout`); a check that has not finished when it expires, and every check after it, gets ERROR "not run: timeout after 30s". SIGINT or SIGTERM cancels the run the same way: checks that have not finished get ERROR "interrupted" with the hint "re-run; the cluster was not changed" (after a create answer that was not a verified dry run: "re-run; a create was not verified as a dry run, so list leftovers: kubectl get pods,services -n <the namespace> -l app.kubernetes.io/managed-by=audit-tenant", with the target namespace filled in, D103), the report prints with the results so far, and the exit code follows ADR 0004 as after `--timeout`: 1 when a FAIL was proven before the signal, else 2 when a check did not finish (D63; a signal that arrives after every check finished changes nothing); a second signal exits at once. An API error inside one check makes that check ERROR and the run continues. An SSAR answer is read as the API defines it: `allowed: true` means allowed; `allowed: false` means denied whether or not `denied` is set (RBAC never sets `denied`; an explicit `denied: true` from a webhook authorizer adds "explicit deny" to the reason); a non-empty `evaluationError` makes the check ERROR with the server text unless the answer is `allowed: true`, which stands (D52); an answer that does not echo the question, or that has no `allowed` field, is ERROR, never a denial (D52); a proven grant stays FAIL even when a later question fails, the deadline hits, or the check never returns (each check hands a FAIL to the runner the moment it is proven, D61), and a failed request ends the check's questions (client-go retries each one). Every selected check always appears in the output, whatever happened.

### Exit codes (ADR 0004)

| Code | When |
|---|---|
| 0 | No FAIL and no ERROR. SKIPs allowed (default). |
| 1 | At least one FAIL; or, with `--fail-on-skip`, at least one SKIP. `--fail-on-skip` is the opt-in gate for pipelines that must not accept an unproven namespace; the summary line then says "N skipped, counted as failures (--fail-on-skip)" and `-o json` reports the resulting `exitCode`. |
| 2 | At least one ERROR and no FAIL; or the run could not start: bad flags (`--as-group` with no user to impersonate, from `--as` or the kubeconfig user's `as:`; unknown check ID, unknown `-o`), kubeconfig cannot load, API server unreachable, credentials rejected (401), impersonation refused, namespace not found, or the identity may not create SelfSubjectAccessReviews. Each with a one-line reason and hint on stderr. |

### Checklist output (default, chosen in the spec session)

```
namespace team-a · as team-a-dev (groups: team-a, system:authenticated) · cluster kind-dev

PASS  AT-01  No cluster-scoped access            RBAC denied all 4 actions
FAIL  AT-05  NodePort services blocked           a NodePort Service was accepted in a dry run
      fix    add a policy that rejects type: NodePort on create and update, or remove `create`, `update` and `patch` on services from the tenant role
SKIP  AT-09  Pod Security Admission enforced     cannot read namespace labels (forbidden)
      fix    grant `get` on namespace team-a to this identity, or run with --as <admin>

12 passed · 1 failed (AT-05) · 1 skipped (AT-09) · 0 errors · exit 1
MTB IDs and layers: -o wide · machine output: -o json, -o policyreport
```

Rules: counts are per result, not per check family (ten checks produce fourteen results, because AT-04 has five); one line per result in ID order; AT-04 prints its five sub-results; a `fix` line under every FAIL, SKIP and ERROR; a `note` line, never cut, under a result that names what it did not test (after the `fix` line when both appear, D86); header line names namespace, identity (with `(unverified)` when SelfSubjectReview failed, `(self)` without `--as`) and cluster context; the summary line lists up to three failed IDs and up to three skipped IDs, then "and N more"; the line after it names the next commands. Color (green, red, yellow, magenta for ERROR) only when stdout is a terminal, `NO_COLOR` is unset and `--no-color` is absent; `-o json` and `-o policyreport` never carry color. On Windows the tool enables virtual-terminal processing on the console before printing color; if that fails, color is off. `--plain` removes color and the `·` separators (ASCII only). Server text in the terminal printers (checklist, wide, plain) has ASCII control characters and ANSI escapes stripped and newlines folded to `; `. The checklist caps a reason at the terminal width minus the fixed columns (minimum 60 characters; 120 when stdout is not a terminal) with `…` and adds the footer line `full reasons: -o wide or -o json` when any reason was cut; `-o wide`, `-o json` and `-o policyreport` keep the full text. In self mode, when AT-03's cluster-wide wildcard is allowed, the header adds: `this identity looks like a cluster admin; add --as to test a tenant`.

`-o wide` adds two columns after the ID: MTB ID and deciding layer (`RBAC`, `admission (PSA)`, `admission (webhook: kyverno-...)`, `admission (policy: <name>)`, `admission (quota: <name>)` (D68), `config`, `-`).

### PolicyReport (`-o policyreport`), ADR 0008

`apiVersion: wgpolicyk8s.io/v1alpha2`, `kind: PolicyReport`, `metadata.name: audit-tenant-<identity slug>` (the identity lowercased with every character outside `a-z0-9-` replaced by `-`, truncated to 54 characters plus an 8-character hash of the full identity when truncated), `metadata.namespace: <target>`, labels `app.kubernetes.io/managed-by: audit-tenant`, annotations `audit-tenant.dev/identity`, `audit-tenant.dev/groups`, `audit-tenant.dev/verified` and `audit-tenant.dev/tool-version`. A re-run for the same identity replaces its own report; reports for different identities coexist in the namespace (eng review, D27). `scope` references the Namespace. One `results[]` entry per result: `policy` = check ID (for example `AT-04.2`), `rule` = MTB ID (omitted when `-`), `result` = `pass|fail|skip|error`, `severity` = `high|medium|low`, `category: multi-tenancy`, `source: audit-tenant`, `message` = reason, `timestamp`, `properties: {layer, hint, name, identity}`. `summary` holds the four counts. Printed to stdout; the user applies it. The tool never writes it.

## 7. Benchmark plan

Numbers in `BENCHMARK.md` come only from runs of this code.

- **What we measure.** Wall time of a full ten-check run on kind: median and maximum of 5 consecutive runs, target median under 10 s. API requests per run: every HTTP request that passes the safety transport, including discovery, the identity lookup, pagination pages and any client retry (client-go retries are left at their defaults and counted as requests, except that a create is never resent, D103); target at most 40. Write requests per run: a write is any POST, PUT, PATCH or DELETE whose query lacks `dryRun=All`; SSAR and SelfSubjectReview POSTs persist nothing and count as reads; the number must be 0 and the safety test fails otherwise. Binary size per platform.
- **Baselines.** `kubectl-mtb` run on the same kind cluster where it still builds; otherwise record "does not build against 1.37" as the finding. Popeye and Kubescape are not like-for-like; we list them as "different scope" rather than compare numbers.
- **Data and environment.** kind with `kindest/node:v1.37.x`, the fixtures in `test/e2e/`, GitHub Actions `ubuntu-latest`. Commands and versions recorded with each row.
- **Repeat it.** `make e2e` runs the same job locally; the row's `Command` column holds the exact invocation.

## 12. Acceptance criteria (v0.1.0)
